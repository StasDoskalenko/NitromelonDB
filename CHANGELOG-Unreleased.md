### Highlights

- Every decorator also works with standard (TC39 2023-11) decorators and the `accessor` keyword. Legacy decorators stay the default for now, and on Expo they need no Babel setup at all. See [Decorators](https://stasdoskalenko.github.io/NitromelonDB/docs/Advanced/StandardDecorators).

### BREAKING CHANGES

- SQLite adapter (all platforms): a database file that has tables but schema version 0 (`PRAGMA user_version`) now fails to initialize instead of being silently wiped. Version 0 normally means a new, empty database, so such a file wasn't set up by NitromelonDB, or its header is damaged, and setting it up from scratch deleted every table in it without an error. The adapter now reports it through `onSetUpError` ("... has tables but no schema version ...") and leaves the file alone. `database.unsafeResetDatabase()` is the explicit way to start over. Files with only SQLite's own tables, or Android's `android_metadata`, are still set up as new. Databases with a newer version than the app's schema are still reset, as before.
  - When this happens: the database path holds a file NitromelonDB didn't create. For example, an Electron app that stored data with plain `better-sqlite3` in `userData/app.db` (never setting `PRAGMA user_version`) and switches to NitromelonDB with the same `dbName`. Before, the first launch of the new version deleted every user's data without an error; now setup fails, so the problem shows up in development. Also: a prepopulated database built with the `sqlite3` CLI or DB Browser without setting `user_version`, a file Android's `SQLiteDatabase` created directly, or a damaged file header (rare).
  - It never happens for databases NitromelonDB or WatermelonDB created: they always set the version together with the tables.
- Sync: pulled records with a non-string `id` (for example a number) are now rejected, and the pull fails. Before, they were given a random id, so they were already broken, just silently. If your server sends numeric ids, convert them to strings.

### Deprecations

### New features

- Standard decorators ([#182](https://github.com/StasDoskalenko/NitromelonDB/issues/182)): every decorator now also works with standard (TC39 2023-11) decorators, which TypeScript 5+ uses when `experimentalDecorators` is off and Babel compiles with `version: '2023-11'`. Legacy decorators stay the default for now (on Expo, `babel-preset-expo` enables them with no Babel setup), and the docs use them. With standard decorators, declare model fields with `accessor` (`@text('title') accessor title`). Models without it keep working under standard decorators, so you can migrate one at a time: plain fields get their getter and setter on each record when it's created, which is slower (about 2 µs per record with five fields in a Node benchmark), and development builds warn once per field. `@lazy` also accepts a getter (`@lazy get comments() { ... }`) in both modes, which stays lazy with standard decorators; on a field, standard decorators compute the value when the record is created. `@experimentalFailsafe` still needs legacy decorators. The decorator types type-check with `experimentalDecorators` on and off. Checked end to end on Hermes: the NotesApp Maestro flows pass with standard decorators, with both `accessor` and plain fields. See [Decorators](https://stasdoskalenko.github.io/NitromelonDB/docs/Advanced/StandardDecorators). The [migration guide](https://stasdoskalenko.github.io/NitromelonDB/docs/Migrating#optional-standard-decorators) has the steps, and a prompt you can copy into a coding agent to do the switch.
- Development builds now report decorators that compiled but don't work. The first record of each model class is checked, and if a decorated field is also a plain property on the record (which hides the decorator, so reads return `undefined` and writes never reach the database, with no other error), NitromelonDB logs an error naming the fields and the fix. The usual causes: TypeScript or esbuild compiling models with `useDefineForClassFields` on (the default for ES2022+ targets; set it to `false`), or a Babel setup that compiles class fields before the decorators run. Production builds skip the check.
- New `destroyTable({ table })` migration step. On SQLite (native, Node and web), it's `DROP TABLE IF EXISTS`. On LokiJS, the collection is removed and its data is deleted from IndexedDB, so it's no longer loaded and parsed on every launch (also if it was already removed from Loki). Migration syncs skip tables and columns destroyed later in the migrated range

### Fixes

- Sync: a pulled changeset is now validated in full before any of it is applied: table and record shape, string ids, and no id listed more than once in a table's `created` / `updated` / `deleted`. Before, an invalid record found halfway through left the records prepared before it broken in memory, and updating them failed until the app restarted.
- Sync: columns set while creating a record (in the `collection.create()` builder) are now recorded in its `_changed` field. When a pull brought a record with the same id as a locally created, not yet pushed one, `_changed` used to be empty, so the remote version won entirely and the local values were lost ([Nozbe/WatermelonDB#1533](https://github.com/Nozbe/WatermelonDB/issues/1533)). Conflicts are now resolved per column, as for locally updated records: locally set columns win, the rest comes from the server. A custom `conflictResolver` receives this per-column result as `resolved`. `_changed` is now also non-empty in pushed `created` records (servers ignore it), and it's still reset when the record is marked as synced. Records whose builder sets `_raw._status` to something other than `created` don't track these columns.
- LokiJS adapter: when a migration fails, the database is no longer saved. Loki's autosave used to keep running after the failed setup and could save the half-migrated database (for example with a destroyed table's data deleted) while its schema version stayed the old one. Saving stops, as after other fatal errors.
- SQLite adapter: after setting up the database failed, `database.unsafeResetDatabase()` now sets it up from scratch, and `database.readyPromise`, `isReady` and `seed` then behave as on a fresh install. On native and Node, this works after any failed setup: a failed migration, or a corrupt or unrecognized file (Node used to fail with `No driver for tag N`). On Node, it also recovers files too damaged to open ("file is not a database", "malformed"). On web, it works for a database with tables but no schema version; after a failed migration or a corrupt file, the reset still fails (`No wa-sqlite driver with tag N`), as before. Until the database is set up, every other database call fails with the setup error instead of reaching the database. On native, that changes release builds: debug builds stopped at an assertion, but release builds compile it out, so those calls used to run against the database as it was (after a failed migration, still on the old schema).
- SQLite Node adapter (Node.js, Electron, Jest): `unsafeResetDatabase()` on a file-backed database no longer breaks other connections to the same file ([#172](https://github.com/StasDoskalenko/NitromelonDB/issues/172)). It used to delete and recreate the file, which failed with `EBUSY` on Windows and elsewhere left the other connections on the deleted file, reading stale data until their next write failed with `SQLITE_READONLY_DBMOVED`. It now wipes the database in place, like the native adapters. In one transaction, it drops every table and view and sets up the new schema, so other connections see either the old database or the new one, never one without tables. It then runs `VACUUM` (skipped if another connection is still reading after the busy timeout). A corrupt database file can't be wiped in place, so for that case it still recreates the file, as before. (A file too damaged to open at all still can't be reset through the adapter, also as before.)
- The deprecated `@action` decorator no longer throws `Cannot read properties of undefined (reading 'table')` when it decorates a method of a `Collection` subclass. It now gets the table name when the method runs, like `@writer` and `@reader` ([#84](https://github.com/StasDoskalenko/NitromelonDB/issues/84)). Its deprecation warning now names `@action` ("Use @writer instead") instead of `Database.action()`, which `@action` users never call directly. Still once per app run and only in development.
- Android: release builds with R8 (`minifyEnabled`, which Expo SDK 58 now turns on by default) no longer abort on the first database open with `ClassNotFoundException: com.nitromelondb.NativeDatabasePath`. The library now ships consumer ProGuard rules that keep the classes and methods its C++ code finds by name over JNI.
- Sync: With `_unsafeBatchPerCollection`, pulled changes are now committed in batches one after another, each prepared right before it is committed, instead of all at once. Before, every batch was prepared up front and committed concurrently, so a failed batch left an arbitrary subset applied and the rest prepared in the record cache. Now a failed batch leaves the following ones untouched; the batches committed before it stay committed, as before. Deleted records are also cleaned up before the changes are applied instead of concurrently, so a failed cleanup no longer lets batches commit after the sync writer has returned. Observers are notified once per pull instead of once per table and batch.

### Performance

- Sync: `markLocalChangesAsSynced` and applying pulled changes to locally deleted records now take linear time in the number of local changes, instead of quadratic. Pushed records are looked up in a Map by table and id instead of scanning `affectedRecords`, and the locally deleted ids are kept in a Set. This speeds up syncs with many local changes or deletions ([#183](https://github.com/StasDoskalenko/NitromelonDB/issues/183), [#192](https://github.com/StasDoskalenko/NitromelonDB/pull/192) by [@joker-777](https://github.com/joker-777)).

### Changes

- New [`examples/sync-server`](https://github.com/StasDoskalenko/NitromelonDB/tree/master/examples/sync-server): a reference sync backend in TypeScript (Hono and SQLite) that follows every rule in [Sync / Backend](https://github.com/StasDoskalenko/NitromelonDB/blob/master/docs-website/docs/docs/Sync/Backend.md). `src/sync.ts` has no framework dependencies, so it can be copied into an Express, Fastify or Nest backend. The Backend docs now link to it, and recommend sending every pulled record as `updated` (with `sendCreatedAsUpdated: true`): with the suggested `created` / `updated` split by `server_created_at`, the app's own pushed records come back as `created` on its next pull, and a record deleted in between (create, sync, delete, sync) is recreated, so the deletion is lost.
- Docs: the migration guide from WatermelonDB covers the Babel decorators setup that breaks on Expo SDK 56+ and RN 0.87+ (remove the decorators plugin on Expo), and has an optional section on standard decorators, with a prompt for coding agents. The Decorators page covers both modes, and what to do when decorators don't work. `@lazy` examples in the docs are now getters, which are lazy in both modes.
- Docs: the Model page explains why TypeScript model fields need `!`, and how a field's type can drift from its schema column without any error (optional columns typed without `null`, wrong types that are silently stored as `''` / `0` / `false`, misspelled or removed columns, missing decorators), with how to avoid each today. A plan for checking fields against the schema at compile time is in `plans/typed-schema-fields.md`.
- Examples: NotesApp no longer has a `babel.config.js`. Expo's default Babel setup is all it needs, decorators included.

- Docs: new [Custom Collections](https://github.com/StasDoskalenko/NitromelonDB/blob/master/docs-website/docs/docs/Advanced/CustomCollections.md) page covering `static associatedCollectionClass`, which lets a Model use its own `Collection` subclass for table-level `@writer` / `@reader` methods and named queries.
- Docs: the docs site now publishes [`llms.txt`](https://stasdoskalenko.github.io/NitromelonDB/llms.txt) and [`llms-full.txt`](https://stasdoskalenko.github.io/NitromelonDB/llms-full.txt) for AI coding agents, plus a plain Markdown copy of every page (`.../docs/Writers.md`). They're generated at build time from the same sources and sidebar, so they stay in sync. Every page now also has a meta description.
- Docs: the [Installation](https://stasdoskalenko.github.io/NitromelonDB/docs/Installation) guide's Babel setup for decorators no longer breaks the build ([#182](https://github.com/StasDoskalenko/NitromelonDB/issues/182)). Following it on Expo SDK 56+ or RN 0.87+ failed on every field declared with `!` (`@field('amount') amount!: number`) with `Definitely assigned fields cannot be initialized here, but only in the constructor`. Expo apps now need no Babel setup at all: `babel-preset-expo` already enables decorators with the class field plugins they need, in the right order, and adding `@babel/plugin-proposal-decorators` yourself runs it too early, so delete it from your config. Bare React Native apps need four plugins in a fixed order: `@babel/plugin-proposal-decorators` (`legacy: true`), then `@babel/plugin-transform-class-properties`, `@babel/plugin-transform-private-methods` and `@babel/plugin-transform-private-property-in-object` (all `loose: true`). The guide also no longer asks for a manual R8 keep rule, since the library ships its own.
- `database.experimentalBatchNotifications()` now merges all changes made within it into one notification (one call per `experimentalSubscribe` subscriber, one emission per changed collection) instead of replaying one notification per batch.

### Internal

- NotesApp syncs with `examples/sync-server` (a Sync button in the header), and a new Maestro flow, `maestro/sync.yaml`, checks both directions on iOS and Android in CI: a note created on the server shows up on the device, and a note created on the device reaches the server. `yarn start:notes-app` in `examples/sync-server` starts the server with the NotesApp schema.
- End-to-end sync tests (`yarn test:sync-e2e`, new `Sync end-to-end` CI job on Linux): real `Database` instances on the SQLite (Node) and LokiJS adapters sync over HTTP with `examples/sync-server`. They cover each numbered rule in the Backend docs, conflicting edits on two devices with `409` and retry, edit vs. delete in both orders, lost push responses, offline devices, migration syncs, and a seeded random test on three devices that checks every device ends up with what the server has, with no deletion undone and nothing lost. A `test.failing` case documents the deletion being lost when the server sends records as `created`.
- Native: removed `deleteDatabaseFile()` from the iOS, Android and Windows platform code ([#91](https://github.com/StasDoskalenko/NitromelonDB/issues/91)). Nothing called it, and its three implementations disagreed on when to throw (Android and Windows never did, despite the documented contract). Resetting a database stays in place on the open connection.
- `yarn test` now also runs on Windows in CI (`JavaScript tests (Windows)`), so the SQLite Node adapter's Windows-only fixes (drive-letter paths, file handles blocking deletes) are covered ([#90](https://github.com/StasDoskalenko/NitromelonDB/issues/90)).
- `yarn test:babel-docs` (run in CI) compiles and runs a decorated model through the bare React Native and Expo Babel configs shown in the Installation guide and the Standard decorators page, read from the docs themselves, so the documented setup can't silently break again ([#182](https://github.com/StasDoskalenko/NitromelonDB/issues/182)).
