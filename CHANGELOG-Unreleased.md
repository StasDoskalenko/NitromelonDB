### New features

- **Agent skills** for AI coding agents (Claude Code, Cursor, Codex and others), in `skills/`. Install with `npx skills add StasDoskalenko/NitromelonDB`. `nitromelondb-install` adds NitromelonDB to a new app: packages, decorators and TypeScript setup for the platform (Expo, Expo web, bare React Native, Vite, Webpack, Node, Electron, Windows), Expo plugin, schema, migrations, models, the `Database`, `DatabaseProvider`, and a data layer on observing hooks and batched writers. `nitromelondb-schema` designs the schema from the app's types, API and stored state, and makes every later change with its migration. `nitromelondb-sync` builds both sides of sync: the backend's pull and push endpoints (from the reference server's rules) and the app's sync engine (one sync at a time, retry, triggers, logout), with two-device tests. `nitromelondb-migrate-from-watermelondb` does the WatermelonDB migration (packages, imports, mocks, patches, old native linking and config plugins, adapter, Babel), then proposes what NitromelonDB adds. `nitromelondb-migrate-decorators` moves models to standard decorators. `nitromelondb-audit` reviews an app's setup and reports problems with `file:line`. `nitromelondb-indexes` finds missing and unused indexes and writes the migration. The docs now lead with the agent route: Installation, the README, Setup, Schema and Sync point to the skills first, then the manual steps. See the new Agent skills page, and the new Building a fast app section of Performance. The coding-agent prompt for standard decorators moved from the migration guide to the Decorators page
- **Paginated pulls** (#50), opt-in on both sides. Pass `paginatedPulls: true` to `synchronize()`, and have the server page only for apps that ask (`paginated=true` in the docs and examples). A page comes with a `nextCursor`, and `synchronize()` calls `pullChanges()` again with `cursor` until a page comes without one. Each page is applied in its own write (one page in memory at a time), `lastPulledAt` only moves after the last page, local changes are pushed once at the end, and a sync that stops halfway continues from the saved cursor next time (or starts over after an app update changed the schema). Without `paginatedPulls`, `nextCursor` is ignored as before, and development builds warn. They also warn about `experimentalHasMore` (from an unreleased WatermelonDB pull request), which isn't supported. The Sync docs and examples use paginated pulls by default: the example sync server pages for apps that ask (`SYNC_SERVER_PAGE_SIZE`, 1000 by default; keyset pages by `(last_modified, id)` over a fixed snapshot timestamp), and NotesApp asks

### Changes

- Docs (Installation): the Babel decorator plugins are installed as `@^7`, since npm's `latest` is Babel 8 and React Native's preset is on 7 (npm failed with `ERESOLVE`). New notes for Vite 8, which has no Babel step: decorators come from `tsconfig`, apps with `"type": "module"` need `legacy.inconsistentCjsInterop` for default imports from `nitromelondb`, and standard decorators go through `@rolldown/plugin-babel`. Web apps without Expo are pointed at the LokiJS adapter
- Sync: `log.newLastPulledAt` is now set once the pulled changes are applied, not before

### Internal

- CI: Yarn waits 3 minutes per download (was 1) and retries 5 times (was 3), and the jobs that install the sync server cache Yarn's downloads. A timed-out download from npm crashed Yarn and failed the NotesApp iOS (Maestro) job on master
- NotesApp web: a Playwright test where two devices on wa-sqlite (two browser profiles) sync through the reference sync server: first syncs in both directions, a note reaching the other device, both syncing at once (a rejected push resolved by syncing again), and synced data surviving a reload. The sync server gets an optional `SYNC_SERVER_CORS_ORIGIN` so web apps can call it (`yarn start:notes-app` allows any origin)
- CI: the iOS Maestro job recovers when Maestro's XCTest driver dies mid-run (an XCTest screenshot timeout under load ends the driver, and every remaining flow fails; mobile-dev-inc/maestro#3538, not fixed in Maestro 2.12.1). If the driver's logs show it died, the flows that didn't pass run once more with a freshly installed driver, with a warning on the job. A run where the driver stayed up is never retried. Each attempt keeps its own diagnostics folder
- Sync end-to-end tests for paginated pulls on SQLite and LokiJS: first and incremental syncs in pages, server changes and local edits between pages, an interrupted pull continuing from its cursor, an app update in the middle of one, a push conflict with a change made during the pull, and batched pulls. The random convergence test also runs against a server sending pages of 7, with pulls interrupted halfway
- Sync end-to-end tests for a custom `conflictResolver` with an app-side retry loop (called for every pulled update, resolving on the retry after a rejected push, giving up and pushing later, never asked about deletions) and for migration syncs turned on after an app shipped (`migrationsEnabledAtVersion` later than the version a device logged in on, and the fallback when a device has no noted version). The Sync docs now spell out what a `conflictResolver` is called with and when it must mark a column as changed
- CI: the Android flashlight benchmark adjusts CPU, FPS and score for the CI machine's speed, like the iOS benchmark does with WatermelonDB: a fixed NotesApp build (v0.32.0, built once and cached) runs in turns with each commit's, and how it compares with its usual values is that job's machine factor. The PR comment compares the adjusted values with the median and range of master's last 10 runs (🟢 better, 🟡 within range, 🔴 clearly worse, ⬆️ / ⬇️ for the direction), and the performance page charts them (once enough runs have the reference)
- CI: the iOS sync benchmark compares NitromelonDB with WatermelonDB run by run. Each metric's speedup is the median of the speedups of the runs side by side, which varies 2.5% from job to job for the stress test (8.1% for best runs, which the comment and charts compared before). On the performance page, each metric is adjusted for the CI machine by WatermelonDB's result on the same workload instead of a mix of four workloads, and points are median runs. The chart showed a 19% stress-score drop at #218 that wasn't there: #220 began recording best runs in the same job, and the machine factor's history median mixed them with older medians. With this change, the stress score's job-to-job variation goes from 15% to 7%, Sync 50k from 10% to 4%

- NotesApp Windows example: React Native Windows 0.85.0 → 0.85.2 (dependency bumps and a RichEdit load-path hardening; no API changes). Its default Hermes build is unchanged, so the `HermesVersion` pin in `ExperimentalFeatures.props` stays. The Windows e2e suites pass on it.

- Example apps (NotesApp, NotesApp_windows, benchmark) and the iOS test project now use `react-native-nitro-modules` and `nitrogen` 0.37.2. The generated Nitro code only changes in its header comments. On Windows, `NitromelonDB.vcxproj` builds against both Nitro source layouts, so apps on Nitro 0.35–0.36 keep working while apps on 0.37 build too.

- NotesApp Windows example: pinned Hermes is now `0.0.0-2610.28001-08ee40a5` (was `0.0.0-2605.6002-2279da22`), the first published build with the fix for the `HadesGC::OldGen::search` crash that RNW 0.85's default Hermes has ([hermes-windows#392](https://github.com/microsoft/hermes-windows/issues/392), fixed in [#395](https://github.com/microsoft/hermes-windows/pull/395)). The Windows e2e suites pass on it. The pin can go once RNW's own default is that build or newer.
