### New features

- **Database encryption** (opt-in, iOS, Android, Windows, Node and Electron, #60), in the SQLCipher 4 format (AES-256, HMAC-SHA512, PBKDF2):
  - **The encryption build.** Add `"nitromelondb": { "encryption": true }` to your app's `package.json` (or set `NITROMELONDB_ENCRYPTION=1`) and rebuild the native app: iOS, Android and Windows then compile [SQLite3 Multiple Ciphers](https://github.com/utelle/SQLite3MultipleCiphers) 2.7.1. Without the switch nothing changes, and apps contain no cryptography from NitromelonDB. That is why it is opt-in: Apple's export-compliance answer covers every library an app links. In the encryption build, iOS uses the bundled SQLite instead of the system one, with Apple's behavior-affecting options (WAL `synchronous=NORMAL`, FTS3/4/5, R*Tree, math functions, 500,000 bound variables), and SQLite's symbols are hidden, so it doesn't clash with expo-sqlite, op-sqlite, SQLCipher or the system SQLite. Size per arm64 slice: about +1.2 MB on iOS, +110 KB on Android. Passing `encryption` to the Expo config plugin fails with a pointer to `package.json`.
  - **The passphrase.** `new SQLiteAdapter({ encryption: { passphrase } })` opens or creates an encrypted database. The passphrase can be a function (Keychain, biometric prompt, server): every database call waits for it. An empty passphrase, a wrong or missing one, or a plain database where an encrypted one was expected fails setup with `error.code` (`encryption_key_invalid`, `encryption_key_required`, `database_not_encrypted`) and never changes or resets the file. A passphrase given to a build without the switch throws `encryption_unavailable` naming the fix, instead of writing a plaintext database. LokiJS and the web refuse the option.
  - **Existing users.** With `ifUnencrypted: 'open'`, a plain database from an earlier app version opens as it is, and `database.unsafe_EncryptDB(passphrase)` (in a writer) encrypts it in place, keeping every record. The same call changes the passphrase of an encrypted database, and `database.unsafe_DecryptDB()` decrypts (by writing a decrypted copy and replacing the file with it, so it needs free space for the copy). Reads made meanwhile wait, the JS thread doesn't block, and `encryption.events` (`onStart` with the size, `onSuccess`, `onError`) report it. Killing the app in the middle leaves the database either as it was or fully re-keyed, never damaged: the next launch rolls back an interrupted encryption before opening the file. Also `database.isDBEncrypted()`, `SQLiteAdapter.isEncryptionAvailable()` and `SQLiteAdapter.getDatabaseEncryptionState(dbName)` (reads the file header only).
  - **Node and Electron.** Install `better-sqlite3-multiple-ciphers` (better-sqlite3 with the same SQLite3 Multiple Ciphers and SQLite versions) and NitromelonDB uses it instead of `better-sqlite3`: the same `encryption` option, errors and file format, so a database moves between Node and the apps. Without it, a passphrase throws `encryption_unavailable`, and nothing else changes. With it, a file that isn't plain SQLite, opened without a passphrase, fails with `encryption_key_required` instead of being treated as damaged; a re-key refuses while another adapter in the process has the file open
  - **Interoperable with SQLCipher.** Files are in SQLCipher 4's own layout, so the `sqlcipher` shell and DB Browser for SQLite open them, and databases that other SQLCipher libraries encrypted with SQLCipher 4's defaults (Room/SQLCipher, expo-sqlite `useSQLCipher`, op-sqlite `sqlcipher`) open with their passphrase. Tested with a database written by SQLCipher 4 itself. Like SQLCipher, encrypted connections zero deleted content (`secure_delete`)
  - **Progress.** `encryption.events.onProgress({ operation, progress })` reports how far `unsafe_EncryptDB()` and `unsafe_DecryptDB()` have come, from 0 to 1, about every 200 ms (iOS, Android, Windows). SQLite reports no progress for a re-key, so native code estimates it from what has been written (the decrypted copy, the rollback journal, and while encrypting the temporary encrypted copy first): it only moves forward. Listeners on `encryption.events` that throw are logged and no longer stop the operation's callback. `adapter.subscribeToEncryptionEvents(events)` adds more listeners.
  - **`useEncryption()` hook** (`nitromelondb/react`, `nitromelondb/hooks`): `{ state, operation, progress, error, encrypt, decrypt }`. `state` is `'loading'`, `'encrypted'`, `'unencrypted'` or `'unavailable'`; it follows every encrypt and decrypt, not only its own.
  - **iOS App Groups.** `encryption: { plaintextHeader: true }` keeps the first 32 bytes of the file (SQLite's header) plain, as SQLCipher's `cipher_plaintext_header_size` does, so that iOS doesn't kill an app that is suspended with the database open in a shared container. The key's salt moves to `<database>-nitromelon-salt` next to it (written before the database depends on it, deleted when it no longer does); without it, opening fails with the new `encryption_salt_missing` and leaves the file alone. An encrypted database in the other layout is re-keyed into the one asked for when it's opened (with `encryption.events`), and back when the option is turned off. Killed at any point, every change of layout opens in the old or the new one. Not on Node and Electron, which refuse the option and such a file with `encryption_unavailable`.
  - **Agent skill `nitromelondb-encryption`**: adds encryption to an app step by step (build switch, passphrase in the Keychain / Keystore, existing users with progress, setup errors without resets, logout, App Groups) and checks the file on disk. `nitromelondb-audit` checks encryption setups (S11), and `nitromelondb-migrate-from-watermelondb` handles apps that patched WatermelonDB for SQLCipher.
  - New docs section, Encryption (its own sidebar category): why it's opt-in, setup per platform, keeping the passphrase in the Keychain/Keystore, migrating existing users, changing the passphrase and logging out, more than one connection, error codes, how it works, and Apple's export-compliance table

### Internal

- Encryption upgrade test (`scripts/ci-notesapp-encryption-upgrade.sh`), new steps: Windows now runs step 9 too (a Turbo Login sync into the encrypted database: the script starts the sync server and exempts the app from loopback isolation); on iOS, NotesApp opened with a `nitromelonPlaintextHeader` launch argument moves its database to the `plaintextHeader` layout and back, checked on disk (SQLite's header, encrypted from byte 32, the salt file, and no salt file afterwards); and on every platform, about 135 MB of filler notes (a new NotesApp button), then decrypting and encrypting must each report progress that only moves forward (`encryption-progress`)
- `yarn benchmark:encryption` (`native/benchmarks/EncryptionBenchmark.cpp`): the same workload on the default build, the encryption build without a key and with one, plus encrypt / re-key / decrypt times. Results in docs/Encryption/HowItWorks ("What it costs").
- Native SQLite is compiled through `native/shared/NitromelonSqlite.c` on every platform, with all options in `NitromelonSqliteConfig.h`, and native code includes `NitromelonSqlite.h` instead of `<sqlite3.h>`. `native/vendor/sqlite3mc` holds the sqlite3mc amalgamation (`scripts/vendor-sqlite3mc.mjs`, checked against the release's `SHA256SUMS`). The weekly bump workflow moves both vendored copies together, so the default and encryption builds are always on the same SQLite. `yarn test:native-unit` builds and tests both, checks they share a SQLite version, that the default build has no encryption, and that the encryption build encrypts (SQLCipher 4 defaults, wrong key fails, in-place encrypt, re-key and decrypt) and exports only `nitromelon_`-prefixed symbols
- Releases: release lines. **Cut Release Line** creates `release/X.Y.x` from a published tag, and Prepare Release and Publish Release run on it as on master, so `X.Y.*` versions (an alpha promoted as it was tested, hotfixes) ship without master's newer work. After a line's release, Publish Release opens a PR recording it in master's `CHANGELOG.md`. npm channel tags only move forward (an older line's release gets `latest-X.Y`), Prepare Release on master refuses versions that belong to a line, and CI runs on pushes to lines (`.github/workflows/README.md`, Release lines)
- Encryption: the native open and re-key logic is in `native/shared/SqliteEncryption.cpp`, tested by `yarn test:native-unit` in both builds, including killing a process in the middle of encrypting, re-keying and decrypting. New CI jobs build NotesApp for iOS and Android with the encryption build next to the plain one, then, on a simulator and an emulator, install the plain build, upgrade it to the encryption build, encrypt the database, and check the file in the app's data folder between steps (`scripts/ci-notesapp-encryption-upgrade.sh`, flows in `examples/NotesApp/maestro-encryption`). NotesApp shows the encryption state and an Encrypt button in the encryption build, and a setup error screen instead of loading forever. The Nitro adapter's `setStoreWholeNumbersAsIntegers` no longer opens the database, so opening errors come from `initialize`
- Agent instructions: one `CLAUDE.md` per folder (each `AGENTS.md` is a symlink to it, for Codex and Cursor), replacing the duplicated `.claude/rules` and the per-prompt Claude Code hook. New guides for `examples/NotesApp_windows`, `native/windows`, `.github/workflows` and `examples/benchmark`.
