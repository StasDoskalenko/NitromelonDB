# Migrate from WatermelonDB to NitromelonDB

NitromelonDB is a maintained fork of WatermelonDB. Models, schema, queries, writers and sync work the same way. What changes is the package name and how the native code is linked: autolinking does all of it now.

The app's data is not migrated or touched. Existing SQLite files, the schema version, migrations and models keep working.

Reference (plain Markdown): https://stasdoskalenko.github.io/NitromelonDB/docs/Migrating.md

## Step-by-step procedure

Follow the steps in order. Don't skip the checks in step 1.

### 1. Check the prerequisites

Read `package.json`, and `app.json` / `app.config.*` if the app uses Expo.

- React Native **0.83 or newer**.
- **New Architecture** on. If you find `newArchEnabled=false` (`android/gradle.properties`), `"newArchEnabled": false` (Expo config) or `RCT_NEW_ARCH_ENABLED=0` (Podfile or CI env), it's off.
- iOS deployment target **15.1+**, Android `minSdkVersion` **24+**.
- Expo apps need a development build or EAS. Expo Go can't load NitromelonDB.

If any of these isn't met, stop and tell the user what to upgrade first. Don't start the migration.

Then record three facts you'll need later:

- The package manager (from the lockfile: `yarn.lock`, `package-lock.json`, `pnpm-lock.yaml`, `bun.lock`).
- Expo or bare React Native. For Expo, whether `ios/` and `android/` are committed or generated by prebuild (check `.gitignore`).
- Whether another library in the app uses decorators (MobX, TypeORM, class-validator). It matters in step 6.

### 2. Swap the packages

With the app's package manager:

- Remove `@nozbe/watermelondb`.
- Remove `@morrowdigital/watermelondb-expo-plugin`, or a fork of it, if present.
- Add `nitromelondb`.
- Add `react-native-nitro-modules` unless the app already has it. It must be **0.35.2 or newer**: upgrade it if it's older.

Don't add `rxjs` for NitromelonDB. It brings its own. Leave it if the app's own code imports it.

Remove `@nozbe/with-observables` only if nothing imports it after step 3. `withObservables` is exported from `nitromelondb/react`.

### 3. Replace imports in JS and TS

Replace `@nozbe/watermelondb` with `nitromelondb` in source files, tests and config. Every subpath keeps its name:

```js
// before
import { Database, Q } from '@nozbe/watermelondb'
import SQLiteAdapter from '@nozbe/watermelondb/adapters/sqlite'
import { withObservables } from '@nozbe/watermelondb/react'

// after
import { Database, Q } from 'nitromelondb'
import SQLiteAdapter from 'nitromelondb/adapters/sqlite'
import { withObservables } from 'nitromelondb/react'
```

Search these places, not just `src/`:

- `import` / `require` / dynamic `import()` in `.js`, `.jsx`, `.ts`, `.tsx`, `.mjs`, `.cjs`
- `jest.mock('@nozbe/watermelondb...')` and `jest.requireActual(...)`
- `__mocks__/@nozbe/watermelondb` → move to `__mocks__/nitromelondb` (delete the empty `__mocks__/@nozbe` folder)
- Jest config: `transformIgnorePatterns`, `moduleNameMapper`, `setupFiles`
- `babel.config.js`, `metro.config.js`, ESLint config, `tsconfig.json` `paths`, `.flowconfig`
- `patches/@nozbe+watermelondb+*.patch` (patch-package): delete them, and tell the user which ones existed, because the bug they patched may need checking again

**Don't run this replace on native files** (Podfile, `*.pbxproj`, `*.gradle`, `MainApplication.*`, `AppDelegate.*`). There it produces paths that don't exist. Step 4 deletes those lines instead.

### 4. Delete the old native setup

Delete everything that was added by hand for WatermelonDB. Don't point it at the new package.

**Expo.** In `app.json` / `app.config.*`, replace the old plugin entry (with any options it had) with `"nitromelondb"`:

```json
{ "expo": { "plugins": ["nitromelondb"] } }
```

If `ios/` and `android/` are generated by prebuild, that's all: skip the iOS and Android lists below.

**iOS** (bare React Native, or Expo with committed native folders):

- `ios/Podfile`: delete `pod 'WatermelonDB'`, `pod 'simdjson'` and `pod 'FMDB'` lines that point into `node_modules/@nozbe`. Don't add `pod 'NitromelonDB'`.
- Xcode project: delete `HEADER_SEARCH_PATHS` entries that point into `@nozbe/watermelondb/.../SupportingFiles`.
- Bridging header: if it imports WatermelonDB headers, change the import to `#import <NitromelonDB/NitromelonDB.h>`. Keep it only if native code uses it (Turbo Login, for example).

**Android:**

- `android/settings.gradle`: delete the `:watermelondb-jsi` (and `:watermelondb`) `include` and its `projectDir` line.
- `android/app/build.gradle`: delete `implementation project(':watermelondb-jsi')`.
- `MainApplication.java` / `.kt`: delete the `WatermelonDBJSIPackage` and `WatermelonDBPackage` imports and their `add(...)` / `getJSIModulePackage` code.
- Proguard / R8 rules: change `-keep class com.nozbe.watermelondb.** { *; }` to `-keep class com.nitromelondb.** { *; }`.

**Windows:** remove the old UWP `WatermelonDB.vcxproj` / `WMDatabaseBridge` linking, then follow https://stasdoskalenko.github.io/NitromelonDB/docs/Installation.md (Windows section).

### 5. Update the adapter

Find every `new SQLiteAdapter({ ... })`.

- Remove `jsi: false`. It throws on iOS and Android now.
- `jsi: true` is harmless but does nothing. Remove it.
- Leave `schema`, `migrations`, `dbName` and `onSetUpError` as they are.
- Don't turn on new options here (`storeWholeNumbersAsIntegers`, `seed`). See step 9.

### 6. Fix the Babel decorators setup

WatermelonDB's install guide had apps add `@babel/plugin-proposal-decorators` by hand. What's right now depends on the platform:

- **Expo:** remove `@babel/plugin-proposal-decorators` (and the class-properties plugins added for it) from `babel.config.js`. `babel-preset-expo` already turns legacy decorators on, and since SDK 56 a decorators plugin of your own runs before the preset's and breaks fields declared with `!` (`Definitely assigned fields cannot be initialized here`). If `babel.config.js` has nothing else in it, it can go.
- **Bare React Native:** keep these four plugins, in this order, with these options, and add the missing ones as dev dependencies:

  ```js
  plugins: [
    ['@babel/plugin-proposal-decorators', { legacy: true }],
    ['@babel/plugin-transform-class-properties', { loose: true }],
    ['@babel/plugin-transform-private-methods', { loose: true }],
    ['@babel/plugin-transform-private-property-in-object', { loose: true }],
  ]
  ```

- **Web (Webpack, Vite):** the decorators plugin (`legacy: true`) first, then class properties with `loose: true`.

If another library in the app needs a different decorators setup, don't guess: show the user both and ask.

Stay on legacy decorators during this migration. Moving to standard decorators is a separate, optional change (the `nitromelondb-migrate-decorators` skill).

### 7. Fix what the type checker and tests find

Run the app's type checker and its tests. Fix what's caused by the migration:

- **Flow types.** The package is written in TypeScript and ships its own `.d.ts` files. Remove `@nozbe/watermelondb` from `.flowconfig`. Don't add `tsconfig` `paths` into `node_modules/nitromelondb/src`: that breaks Metro and Jest.
- **Type names**, all from `nitromelondb`: `RecordId`, `TableName<T>`, `ColumnName`, `RawRecord`, `DirtyRaw` keep their names. `Associations` comes from `nitromelondb/Model`. `RelationId<T>` / `$Call<...>` helpers become `RelationId<Model>` (`string`) or `RelationId<Model | null>`. `$Diff`, `$Rest`, `$Shape` become `Omit`, `Partial`, `Pick`. `json()` is generic: `json<TInput, TOutput>(column, sanitizer)`.
- **Assigning `record.id`** works only inside `collection.create()` / `prepareCreate()`. Anywhere else it throws. `_raw.id` and `prepareCreateFromDirtyRaw` still work.

Don't "fix" failures that have nothing to do with the migration. List them for the user.

### 8. Rebuild

A Metro reload isn't enough: the native code changed. Reinstall dependencies with the app's package manager, then ask the user to run the native build, or run it yourself if they asked you to:

```bash
# bare React Native
cd ios && pod install && cd ..
npx react-native run-ios
npx react-native run-android

# Expo
npx expo prebuild --clean
npx expo run:ios
```

Before starting a bundler, check whether one is already running on port 8081 and reuse it.

### 9. Report

Finish with a summary:

- Packages removed and added
- Number of files with rewritten imports, and mocks moved
- Native lines deleted, per file
- Adapter and Babel changes
- Anything you couldn't migrate, deleted patches, and unrelated failures you left alone

Then tell the user about these, without doing them:

- **Android Studio's Database Inspector no longer shows the database.** NitromelonDB ships its own SQLite build. To open the file: https://stasdoskalenko.github.io/NitromelonDB/docs/Advanced/ProTips.md
- **`seed`**: on a database carried over from WatermelonDB, every seed step runs, even if the tables already have user data. Read https://stasdoskalenko.github.io/NitromelonDB/docs/Advanced/Seeding.md before adding it.
- **Recommended next:** `storeWholeNumbersAsIntegers: true` on the adapter (faster number comparisons and sorting), after checking the app's raw SQL, and `experimentalDetectNestedWriters: __DEV__` on the database. The `nitromelondb-audit` skill checks both.

## Checklist

- [ ] `@nozbe/watermelondb` removed, `nitromelondb` and `react-native-nitro-modules` (0.35.2+) installed
- [ ] No `@nozbe/watermelondb` left in JS/TS imports, Jest mocks or config
- [ ] Old Podfile, Xcode header path, Gradle and `MainApplication` entries deleted, nothing added in their place
- [ ] Expo: `"nitromelondb"` plugin instead of the old one
- [ ] `jsi: false` removed
- [ ] Babel decorators set up for the platform (Expo: no decorators plugin; bare React Native: four plugins in order)
- [ ] Type checker and tests pass, or the remaining failures are listed
- [ ] Full native rebuild done or handed to the user
