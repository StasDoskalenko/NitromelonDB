# Migrate from WatermelonDB to NitromelonDB

NitromelonDB is a maintained fork of WatermelonDB. Models, schema, queries, writers and sync work the same way. What changes is the package name and how the native code is linked: autolinking does all of it now.

The app's data is not migrated or touched. Existing SQLite files, the schema version, migrations and models keep working.

Reference (plain Markdown): https://stasdoskalenko.github.io/NitromelonDB/docs/Migrating.md

## Step-by-step procedure

Follow the steps in order. Don't skip the checks in step 1.

### 1. Check the prerequisites

Read `package.json`, and `app.json` / `app.config.*` if the app uses Expo.

- React Native **0.83 or newer**.
- **New Architecture** on. If you find `newArchEnabled=false` (`android/gradle.properties`), `"newArchEnabled": false` (Expo config) or `RCT_NEW_ARCH_ENABLED=0` (Podfile or CI env), it's off.
- iOS deployment target **15.1+**, Android `minSdkVersion` **24+**.
- Expo apps need a development build or EAS. Expo Go can't load NitromelonDB.

If any of these isn't met, stop and tell the user what to upgrade first. Don't start the migration.

Then record three facts you'll need later:

- The package manager (from the lockfile: `yarn.lock`, `package-lock.json`, `pnpm-lock.yaml`, `bun.lock`).
- Expo or bare React Native. For Expo, whether `ios/` and `android/` are committed or generated by prebuild (check `.gitignore`).
- Whether another library in the app uses decorators (MobX, TypeORM, class-validator). It matters in step 6.

### 2. Swap the packages

With the app's package manager:

- Remove `@nozbe/watermelondb`.
- Remove `@morrowdigital/watermelondb-expo-plugin`, or a fork of it, if present.
- Add `nitromelondb`.
- Add `react-native-nitro-modules` unless the app already has it. It must be **0.35.2 or newer**: upgrade it if it's older.

Don't add `rxjs` for NitromelonDB. It brings its own. Leave it if the app's own code imports it.

Remove `@nozbe/with-observables` only if nothing imports it after step 3. `withObservables` is exported from `nitromelondb/react`.

Also check `package.json` for these, which a plain `remove` leaves behind or trips over:

- **A patched dependency.** Yarn 2+ writes patches into the dependency itself: `"@nozbe/watermelondb": "patch:@nozbe/watermelondb@npm%3A0.28.0#~/.yarn/patches/..."`. Remove the whole entry, and delete the patch file under `.yarn/patches/`. pnpm keeps them in `pnpm.patchedDependencies` and `patches/`. Tell the user which patches existed and what they changed (read the diff): the bug may be fixed in NitromelonDB, or may need checking again.
- **`resolutions` / `overrides` / `pnpm.overrides`** with keys that name `@nozbe/watermelondb` (`"@nozbe/watermelondb/@babel/runtime": "..."`) or `@nozbe/simdjson`: delete those keys. Don't carry them over to `nitromelondb/...`. Its dependencies are current.
- **`@nozbe/simdjson`** or **`@nozbe/sqlite`** as direct dependencies: remove them. NitromelonDB vendors both.

### 3. Replace imports in JS and TS

Replace `@nozbe/watermelondb` with `nitromelondb` in source files, tests and config. Every subpath keeps its name:

```js
// before
import { Database, Q } from '@nozbe/watermelondb'
import SQLiteAdapter from '@nozbe/watermelondb/adapters/sqlite'
import { withObservables } from '@nozbe/watermelondb/react'

// after
import { Database, Q } from 'nitromelondb'
import SQLiteAdapter from 'nitromelondb/adapters/sqlite'
import { withObservables } from 'nitromelondb/react'
```

Search these places, not just `src/`:

- `import` / `require` / dynamic `import()` in `.js`, `.jsx`, `.ts`, `.tsx`, `.mjs`, `.cjs`
- `jest.mock('@nozbe/watermelondb...')` and `jest.requireActual(...)`
- `__mocks__/@nozbe/watermelondb` → move to `__mocks__/nitromelondb` (delete the empty `__mocks__/@nozbe` folder)
- Jest config: `transformIgnorePatterns`, `moduleNameMapper`, `setupFiles`
- `babel.config.js`, `metro.config.js`, ESLint config, `tsconfig.json` `paths`, `.flowconfig`
- `patches/@nozbe+watermelondb+*.patch` (patch-package): delete them, and tell the user which ones existed, because the bug they patched may need checking again. If no patches are left, `patch-package` and its `postinstall` script can go too: ask first
- Comments, log tags and UI strings that name WatermelonDB (`'[WatermelonDB] ...'`): leave them unless the user wants them renamed. They aren't part of the migration

**Don't run this replace on native files** (Podfile, `*.pbxproj`, `*.gradle`, `MainApplication.*`, `AppDelegate.*`). There it produces paths that don't exist. Step 4 deletes those lines instead.

### 4. Delete the old native setup

Delete everything that was added by hand for WatermelonDB. Don't point it at the new package.

**Expo.** In `app.json` / `app.config.*`, replace the old plugin entry (with any options it had) with `"nitromelondb"`:

```json
{ "expo": { "plugins": ["nitromelondb"] } }
```

Apps often wired WatermelonDB up with more than that plugin. In the Expo config, also look for:

- **`expo-build-properties`** options that exist for WatermelonDB: an `ios.extraPods` entry for `simdjson` (or anything with a path into `node_modules/@nozbe`), and `android.packagingOptions.pickFirst` for `**/libc++_shared.so`. Delete those entries. If the plugin has no options left, delete its entry too, and remove the `expo-build-properties` package if nothing else uses it. `pickFirst` is sometimes needed by other native libraries: if the Android build fails afterwards with `More than one file was found with OS independent path 'lib/.../libc++_shared.so'`, put that one back.
- **Local config plugins** (`"./plugins/withSomething"`) that wire WatermelonDB by hand: they mention `watermelondb-jsi`, `WatermelonDBJSIPackage`, `@nozbe/watermelondb/native`, `simdjson` or `FMDB`. Delete the plugin entry and the plugin file. If a plugin also does unrelated work, delete only the WatermelonDB part and tell the user.

Outside the Expo config:

- **`react-native.config.js`**: delete `dependencies` entries for `@nozbe/watermelondb`, `@nozbe/simdjson` or `@nozbe/sqlite` (often `platforms: { ios: null }` to avoid a duplicate pod). If nothing is left in the file, delete it.

If `ios/` and `android/` are generated by prebuild, that's all: skip the iOS and Android lists below.

**iOS** (bare React Native, or Expo with committed native folders):

- `ios/Podfile`: delete `pod 'WatermelonDB'`, `pod 'simdjson'` and `pod 'FMDB'` lines that point into `node_modules/@nozbe`. Don't add `pod 'NitromelonDB'`.
- Xcode project: delete `HEADER_SEARCH_PATHS` entries that point into `@nozbe/watermelondb/.../SupportingFiles`.
- Bridging header: if it imports WatermelonDB headers, change the import to `#import <NitromelonDB/NitromelonDB.h>`. Keep it only if native code uses it (Turbo Login, for example).

**Android:**

- `android/settings.gradle`: delete the `:watermelondb-jsi` (and `:watermelondb`) `include` and its `projectDir` line.
- `android/app/build.gradle`: delete `implementation project(':watermelondb-jsi')`.
- `MainApplication.java` / `.kt`: delete the `WatermelonDBJSIPackage` and `WatermelonDBPackage` imports and their `add(...)` / `getJSIModulePackage` code.
- Proguard / R8 rules: change `-keep class com.nozbe.watermelondb.** { *; }` to `-keep class com.nitromelondb.** { *; }`.

**Windows:** remove the old UWP `WatermelonDB.vcxproj` / `WMDatabaseBridge` linking, then follow https://stasdoskalenko.github.io/NitromelonDB/docs/Installation.md (Windows section).

### 5. Update the adapter

Find every `new SQLiteAdapter({ ... })`.

- Remove `jsi: false`. It throws on iOS and Android now.
- `jsi: true` is harmless but does nothing. Remove it.
- `jsi:` set from a variable (`jsi: USE_JSI`, `jsi: Platform.OS === 'ios'`, an env var such as `EXPO_PUBLIC_*`): remove the option. Then follow the variable back: if it only existed to pick the JSI mode, delete it too (the constant, the file that only exports it, and the env var in `.env*`, `eas.json` and CI). There's only one engine now. If other code uses it, leave it and tell the user.
- Code that reads the adapter's private `_dispatcherType`: use the public `adapter.dispatcherType` getter. On iOS, Android and Windows its value is `'nitro'` (not `'jsi'`), and `'wa-sqlite'` on the web. Fix comparisons with `'jsi'` or `'asynchronous'` accordingly.
- Leave `schema`, `migrations`, `dbName` and `onSetUpError` as they are.
- **An encrypted database.** WatermelonDB itself has no encryption, but some apps patched or forked it to use SQLCipher (look for `passphrase`, `key`, `encryption` or `SQLCipher` in the adapter options, patches, Podfile and Gradle files). Such a database won't open with NitromelonDB until encryption is set up, in this same migration: the encryption build switch and `encryption: { passphrase }` ([Encryption](https://stasdoskalenko.github.io/NitromelonDB/docs/Encryption/Intro.md)). A database encrypted with SQLCipher 4's default settings opens with the same passphrase; one with other settings (SQLCipher 3, a raw key, a changed `kdf_iter`) fails with `encryption_key_invalid` and is left alone. Tell the user which case applies, and use the `nitromelondb-encryption` skill for the setup. Without it, the app's first launch fails with `encryption_key_required` (the data stays intact).
- Don't turn on new options here (`storeWholeNumbersAsIntegers`, `seed`). See step 9.

### 6. Fix the Babel decorators setup

WatermelonDB's install guide had apps add `@babel/plugin-proposal-decorators` by hand. What's right now depends on the platform:

- **Expo:** remove `@babel/plugin-proposal-decorators` (and the class-properties plugins added for it) from `babel.config.js`. `babel-preset-expo` already turns legacy decorators on, and since SDK 56 a decorators plugin of your own runs before the preset's and breaks fields declared with `!` (`Definitely assigned fields cannot be initialized here`). If `babel.config.js` has nothing else in it, it can go.
- **Bare React Native:** keep these four plugins, in this order, with these options, and add the missing ones as dev dependencies, on the app's `@babel/core` major version (`@babel/plugin-...@^7` with Babel 7: npm's `latest` is Babel 8, which React Native's preset doesn't use yet):

  ```js
  plugins: [
    ['@babel/plugin-proposal-decorators', { legacy: true }],
    ['@babel/plugin-transform-class-properties', { loose: true }],
    ['@babel/plugin-transform-private-methods', { loose: true }],
    ['@babel/plugin-transform-private-property-in-object', { loose: true }],
  ]
  ```

- **Web (Webpack, Vite):** the decorators plugin (`legacy: true`) first, then class properties with `loose: true`.

If another library in the app needs a different decorators setup, don't guess: show the user both and ask.

Stay on legacy decorators during this migration. Moving to standard decorators is a separate, optional change (the `nitromelondb-migrate-decorators` skill).

### 7. Fix what the type checker and tests find

Run the app's type checker and its tests. Fix what's caused by the migration:

- **Flow types.** The package is written in TypeScript and ships its own `.d.ts` files. Remove `@nozbe/watermelondb` from `.flowconfig`. Don't add `tsconfig` `paths` into `node_modules/nitromelondb/src`: that breaks Metro and Jest.
- **Type names**, all from `nitromelondb`: `RecordId`, `TableName<T>`, `ColumnName`, `RawRecord`, `DirtyRaw` keep their names. `Associations` comes from `nitromelondb/Model`. `RelationId<T>` / `$Call<...>` helpers become `RelationId<Model>` (`string`) or `RelationId<Model | null>`. `$Diff`, `$Rest`, `$Shape` become `Omit`, `Partial`, `Pick`. `json()` is generic: `json<TInput, TOutput>(column, sanitizer)`.
- **Private members** (anything starting with `_`: `collection._cache`, `adapter._dispatcherType`, `adapter.underlyingAdapter._clearCachedRecords`, `database._...`): NitromelonDB ships strict types, so code that reached into WatermelonDB internals often stops type-checking, and some of those members are gone or behave differently. Use a public API where there is one (`dispatcherType`, `unsafeResetDatabase`, `resetObservablesCache`). Where there isn't, don't paper over it with a cast alone: check in `node_modules/nitromelondb` that the member still exists and does the same thing, and list every such place in the report.
- **Assigning `record.id`** works only inside `collection.create()` / `prepareCreate()`. Anywhere else it throws. `_raw.id` and `prepareCreateFromDirtyRaw` still work.

Don't "fix" failures that have nothing to do with the migration. List them for the user.

### 8. Rebuild

A Metro reload isn't enough: the native code changed. Reinstall dependencies with the app's package manager, then ask the user to run the native build, or run it yourself if they asked you to:

```bash
# bare React Native
cd ios && pod install && cd ..
npx react-native run-ios
npx react-native run-android

# Expo
npx expo prebuild --clean
npx expo run:ios
```

Before starting a bundler, check whether one is already running on port 8081 and reuse it.

### 9. Adopt what NitromelonDB adds

The migration is done once the app builds and runs as before. NitromelonDB also has features WatermelonDB didn't, and the app gets faster and safer with them. Scan the app for each item below, and **list what applies, with `file:line` and the change, as a proposal**. Make the changes only for the items the user picks, one at a time, after the migration has been committed or reviewed, so the two diffs stay apart.

Rules behind these: https://stasdoskalenko.github.io/NitromelonDB/docs/Advanced/Performance.md ("Building a fast app").

**Setup**

- `experimentalDetectNestedWriters: __DEV__` on `new Database(...)`, and `true` in the Jest setup: a writer called from another writer without `callWriter()` throws with both names instead of hanging the app.
- `storeWholeNumbersAsIntegers: true` on the SQLite adapter: faster number comparisons and sorting. Check the app's raw SQL first (Performance page, step 1): it's the only thing that can tell the difference. Data on devices converts in the background.
- Hand-made readiness (a `setTimeout` before the first query, an `isDbReady` flag, a warm-up query, reads of adapter internals) becomes `database.readyPromise`, or `useDatabaseReady(database)` in React. If the app has no such code and does nothing database-related at launch, add nothing.
- Data created from the UI on first launch ("if the table is empty, insert defaults") can move to the `seed` option with `databaseSeed()`. **On databases carried over from WatermelonDB every seed step runs once**, so each step must check whether its data is already there (see the Seeding page). Propose it; don't move it without the user's yes.

**Reads**

- A component that `fetch()`es into `useState` (in an effect) shows stale data after the next write or sync: `useQuery(query)` / `useRecord(record)` from `nitromelondb/hooks`.
- Existing `withObservables` code keeps working, and doesn't need to be rewritten. New components can use the hooks. For a function component that only wraps `withObservables` to observe one record or one query, the hook is shorter; propose it only where the user is already changing that code.
- A list re-rendered whole for one row's change: each row observes its own record (`useRecord`, or `withObservables` per row). A sorted list that doesn't re-sort: `useQuery(query, ['column'])` / `observeWithColumns`.
- `(await query.fetch()).length` → `fetchCount()`, `.map(r => r.id)` → `fetchIds()`, a long list sliced in JavaScript → `Q.sortBy` + `Q.take`.
- `findAndObserve(id)` for a record that may not exist (deep links, records arriving by sync) → `findAndObserveOrNull(id)`.
- `database.get('posts')` → `database.get(Post)`: typed, and a typo can't compile.

**Writes**

- Several `await create()` / `update()` in one writer, or in a loop: one `batch()` of `prepareCreate` / `prepareUpdate` / `prepareMarkAsDeleted`.
- A component that opens `database.write()` to set a few fields of one record: `useAtomicWriter(Model, record, builder)`, which also gives `isPending` and `error`. Writers anchored to a record with more logic: `useWriter(record, fn)`, as long as `fn` doesn't call a `@writer` method (it already runs inside a writer).
- Fetching records to delete them one by one: `query.markAllAsDeleted()` (synced) or `query.destroyAllPermanently()` (local only).

**Sync** (if the app calls `synchronize()`)

- `paginatedPulls: true`, once the backend pages for apps that ask (it's opt-in on both sides; the app can ship first). It needs a nitromelondb release newer than 0.32.0: if `SyncPullArgs` in `node_modules/nitromelondb/sync/index.d.ts` has no `cursor`, leave it for later.
- `sendCreatedAsUpdated: true` if the backend sends every record as `updated`.
- One sync at a time, retry once, debounced triggers: the `nitromelondb-sync` skill has the full engine, and checks the backend too.

Then hand over: the `nitromelondb-audit` skill reviews the rest (writer deadlocks, schema drift, sync mistakes), and `nitromelondb-indexes` finds missing indexes.

### 10. Report

Finish with a summary:

- Packages removed and added
- Number of files with rewritten imports, and mocks moved
- Native lines deleted, per file, and Expo config entries, config plugins and `react-native.config.js` entries removed
- Patches and `resolutions` / `overrides` deleted, with what each patch changed
- Adapter and Babel changes
- Anything you couldn't migrate, deleted patches, and unrelated failures you left alone

Then tell the user about these, without doing them:

- **Android Studio's Database Inspector no longer shows the database.** NitromelonDB ships its own SQLite build. To open the file: https://stasdoskalenko.github.io/NitromelonDB/docs/Advanced/ProTips.md
- **`seed`**: on a database carried over from WatermelonDB, every seed step runs, even if the tables already have user data. Read https://stasdoskalenko.github.io/NitromelonDB/docs/Advanced/Seeding.md before adding it.
- **The proposals from step 9**, with the ones the user picked and what was changed for them.

## Checklist

- [ ] `@nozbe/watermelondb` removed, `nitromelondb` and `react-native-nitro-modules` (0.35.2+) installed
- [ ] No `@nozbe/watermelondb` left in JS/TS imports, Jest mocks or config
- [ ] Old Podfile, Xcode header path, Gradle and `MainApplication` entries deleted, nothing added in their place
- [ ] Expo: `"nitromelondb"` plugin instead of the old one, and no WatermelonDB `extraPods`, `pickFirst`, local config plugins or `react-native.config.js` entries left
- [ ] Patches (`.yarn/patches`, `patches/`) and `resolutions` / `overrides` for `@nozbe/*` deleted, and listed in the report
- [ ] No `jsi` option left (literal or from a variable), and no reads of `_dispatcherType`
- [ ] Searching the app for `@nozbe` and `watermelondb-jsi` (outside `node_modules` and the lockfile) finds nothing but comments and strings
- [ ] Babel decorators set up for the platform (Expo: no decorators plugin; bare React Native: four plugins in order)
- [ ] Type checker and tests pass, or the remaining failures are listed
- [ ] Full native rebuild done or handed to the user
- [ ] Step 9 proposals listed with `file:line`; only the picked ones applied, separately from the migration
