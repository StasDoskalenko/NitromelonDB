# Install NitromelonDB in an app

Add NitromelonDB to an app and leave it with a working database: packages, build config, schema, migrations, models, the `Database`, and the React provider.

References (plain Markdown): [Installation](https://stasdoskalenko.github.io/NitromelonDB/docs/Installation.md), [Setup](https://stasdoskalenko.github.io/NitromelonDB/docs/Setup.md), [Schema](https://stasdoskalenko.github.io/NitromelonDB/docs/Schema.md), [Model](https://stasdoskalenko.github.io/NitromelonDB/docs/Model.md). Full index: https://stasdoskalenko.github.io/NitromelonDB/llms.txt

## Step-by-step procedure

Follow the steps in order. Steps 1 and 2 change nothing.

### 1. Make sure this is the right skill

Read `package.json`.

- **`@nozbe/watermelondb` is a dependency:** stop. This is a migration, not an install. Use the `nitromelondb-migrate-from-watermelondb` skill (or the [migration guide](https://stasdoskalenko.github.io/NitromelonDB/docs/Migrating.md)), which keeps the existing data.
- **`nitromelondb` is already a dependency:** don't install it again. Tell the user, and offer the `nitromelondb-audit` skill to check the setup. If they want more tables or models, go to step 6 and add them with a migration (see "Adding to an existing schema" there).

### 2. Find out what the app is, and check the requirements

Work out the platform from the files, and record it. It decides almost every step below.

| Platform | How to tell |
| --- | --- |
| **Expo** | `expo` in dependencies, `app.json` / `app.config.*`. Note whether `ios/` and `android/` are committed or generated by prebuild (`.gitignore`), and whether it uses Expo Router (`expo-router`) |
| **Expo web** | Expo, plus `react-native-web` / `"web"` in the Expo config, or a `web` script |
| **Bare React Native** | `react-native` without `expo` (or with `expo` only for modules), committed `ios/` and `android/`, `@react-native/babel-preset` |
| **Web without Expo** | `vite`, `webpack`, `next`, no `react-native` |
| **Node.js** | no bundler, a server or script entry point |
| **Electron** | `electron` in dependencies |
| **React Native Windows** | `react-native-windows`, a `windows/` folder |

An app can be more than one (Expo with web, for example). Handle each.

Also record:

- The package manager, from the lockfile: `yarn.lock`, `package-lock.json`, `pnpm-lock.yaml`, `bun.lock`. Use it for every install below.
- TypeScript or JavaScript. For TypeScript, its version, and which tool compiles the files the models will live in: Babel (React Native, Expo, most Webpack setups), `tsc` / `ts-node` / `tsx` / esbuild (Node, Vite without a Babel plugin), or `ts-jest`.
- Whether another library already uses decorators (MobX, TypeORM, class-validator, NestJS). If it does, the app already has a decorators setup: read it, and see step 4.
- Where the app keeps its code (`src/`, `app/`, a feature-folder layout), so the new files follow the same layout.

Requirements for React Native and Expo. If one isn't met, stop and tell the user what to upgrade first:

- React Native **0.83 or newer**, with the **New Architecture** on. It's off if you find `newArchEnabled=false` in `android/gradle.properties`, `"newArchEnabled": false` in the Expo config, or `RCT_NEW_ARCH_ENABLED=0` in the Podfile or CI env.
- iOS deployment target **15.1+**, Android `minSdkVersion` **24+**.
- **Expo Go can't load NitromelonDB.** The app needs a development build (`npx expo run:ios`, or EAS). If the team only uses Expo Go today, say so before going on: it changes how they run the app every day.
- Windows: React Native Windows **0.84** (New Architecture). Node 22.11+.

For Node.js and Electron, the only native piece is `better-sqlite3`, which needs a C++ toolchain if no prebuilt binary matches.

### 3. Install the packages

With the app's package manager. Pin nothing by hand beyond what's listed.

| Platform | Dependencies | Dev dependencies |
| --- | --- | --- |
| Bare React Native, Windows | `nitromelondb`, `react-native-nitro-modules` | `@babel/plugin-proposal-decorators`, `@babel/plugin-transform-class-properties`, `@babel/plugin-transform-private-methods`, `@babel/plugin-transform-private-property-in-object` |
| Expo | `nitromelondb`, `react-native-nitro-modules` (with `npx expo install`, so the versions match the SDK) | none |
| Expo web, without Expo Router | also `@expo/metro-runtime` (with `npx expo install`) | none |
| Web without Expo | `nitromelondb` | `@babel/plugin-proposal-decorators`, `@babel/plugin-transform-class-properties` |
| Node.js, Electron | `nitromelondb`, `better-sqlite3` | none |

- `react-native-nitro-modules` must be **0.35.2 or newer**. If the app already has it, check the version and upgrade it if it's older. Don't add it twice.
- Don't add `rxjs`, `lokijs` or `wa-sqlite`. NitromelonDB brings what it needs.
- Don't add `expo-dev-client` unless the user asks. `npx expo run:*` builds a development build without it.

### 4. Set up decorators

Models use decorators (`@field`, `@text`, `@date`, ...). They must be compiled correctly, or fields silently read `undefined`. Use **legacy decorators** (the default) unless the user asks for standard ones, or another library in the app already needs standard ones.

**Expo:** nothing to add. `babel-preset-expo` turns legacy decorators on, with the class field plugins they need, in the right order.

- If there's no `babel.config.js`, don't create one.
- If there is one, keep `presets: ['babel-preset-expo']` and **don't** add `@babel/plugin-proposal-decorators` to `plugins`. A decorators plugin of your own runs before the preset's and, since SDK 56, breaks fields declared with `!` (`Definitely assigned fields cannot be initialized here, but only in the constructor`).

**Bare React Native and Windows:** all four plugins, in this order, with these options:

```js
// babel.config.js
module.exports = {
  presets: ['module:@react-native/babel-preset'],
  plugins: [
    ['@babel/plugin-proposal-decorators', { legacy: true }],
    ['@babel/plugin-transform-class-properties', { loose: true }],
    ['@babel/plugin-transform-private-methods', { loose: true }],
    ['@babel/plugin-transform-private-property-in-object', { loose: true }],
  ],
}
```

Keep any plugins the app already has (Reanimated / Worklets must stay **last**).

**Web without Expo:** decorators first, then class properties in `loose` mode. Webpack: in `babel.config.js` / `.babelrc`. Vite + React: in `@vitejs/plugin-react`:

```js
react({
  babel: {
    plugins: [
      ['@babel/plugin-proposal-decorators', { legacy: true }],
      ['@babel/plugin-transform-class-properties', { loose: true }],
    ],
  },
})
```

If the Vite app uses `@vitejs/plugin-react-swc` (no Babel), or Next.js with SWC, don't guess a config: tell the user, and offer the TypeScript setup below, which those compilers follow.

**TypeScript.** In `tsconfig.json` `compilerOptions`, for legacy decorators:

```json
{ "experimentalDecorators": true, "useDefineForClassFields": false }
```

`useDefineForClassFields: false` matters whenever TypeScript or esbuild compiles the models (`tsc`, `ts-node`, `tsx`, `ts-jest`, Vite without Babel, Bun): it's on by default for `ES2022`+ targets and hides every decorated field. With Babel it's harmless, so set both anyway.

**If another library already set up decorators:** compare its setup with the one above. If they agree, change nothing. If they differ (it needs standard decorators, or different plugin options), show the user both and ask. Don't guess.

**Standard decorators** (only if asked, or if the app is already on them): follow https://stasdoskalenko.github.io/NitromelonDB/docs/Advanced/StandardDecorators.md. Models then declare fields with `accessor`.

### 5. Native and bundler setup

**Expo:** add the config plugin to `app.json` / `app.config.*`, keeping existing plugins:

```json
{ "expo": { "plugins": ["nitromelondb"] } }
```

Only if an iOS simulator build on Apple Silicon fails with `No such module 'ExpoModulesCore'`, change it to `["nitromelondb", { "excludeSimArch": true }]`. Don't add it up front.

**Expo web:**

- Without Expo Router, load `@expo/metro-runtime` on web only: create `webRuntime.web.ts` with `import '@expo/metro-runtime'`, an empty `webRuntime.ts`, and `import './webRuntime'` at the top of the entry file. Expo Router already does this.
- If the app has its own `metro.config.js`, make sure it starts from `getDefaultConfig` from `expo/metro-config`, and that `wasm` is in `config.resolver.assetExts` (push it if it's missing).

**Bare React Native:** nothing. Autolinking links everything. Don't add Podfile lines, Gradle lines, `MainApplication` code or ProGuard rules.

**Windows:** `react-native-nitro-modules` has no Windows project, so tell autolinking to skip it in `react-native.config.js`, keeping the existing `project.windows`:

```js
const { windowsAppDependencies } = require('nitromelondb/windows-autolink')

module.exports = {
  // ...existing config...
  dependencies: windowsAppDependencies(),
}
```

**Electron:** SQLite runs in the main process, behind IPC. Set it up as in https://stasdoskalenko.github.io/NitromelonDB/docs/Setup.md (section "Electron (SQLite)"): `RemoteAdapter` in the renderer, `SQLiteAdapter` in the main process, and a `preload.js` bridge. Add `npx electron-rebuild -f -w better-sqlite3` to the development setup (README or a `postinstall` script, after asking).

### 6. Create the schema, migrations and models

Put these in one folder that fits the app's layout, for example `src/db/` (`model/` is the docs' name and fine too). Use `.ts` in TypeScript apps.

**Which tables?** If the user described their data, model that. If not, ask what the app stores. Don't invent example tables (posts, comments, tasks) in a real app. If the user only wants the library installed for now, create one small table they agree on, so the setup can be checked in step 9, and say it can be renamed before the first release.

Schema rules for each table:

- Table names are plural and `snake_case` (`posts`, `blog_posts`). Column names are `snake_case`. Relations are `<singular>_id` columns of type `string`.
- Don't declare `id`, `_status` or `_changed`: every table has them.
- Column types are only `string`, `number` and `boolean`. Dates are `number` columns named `*_at`. Mark optional columns `isOptional: true`.
- Add `isIndexed: true` on relation (`_id`) columns that will be queried, and on columns the app looks records up by. Nothing else yet.
- `created_at` / `updated_at` (`number`) are filled in automatically if declared, with `@readonly @date` fields on the model.

```ts
// schema.ts
import { appSchema, tableSchema } from 'nitromelondb'

export default appSchema({
  version: 1,
  tables: [
    tableSchema({
      name: 'posts',
      columns: [
        { name: 'title', type: 'string' },
        { name: 'body', type: 'string', isOptional: true },
        { name: 'is_pinned', type: 'boolean' },
        { name: 'created_at', type: 'number' },
        { name: 'updated_at', type: 'number' },
      ],
    }),
    tableSchema({
      name: 'comments',
      columns: [
        { name: 'body', type: 'string' },
        { name: 'post_id', type: 'string', isIndexed: true },
      ],
    }),
  ],
})
```

Create the migrations file now, empty, and pass it to the adapter from day one. Every schema change after the first release needs a migration here, and an app that never passed `migrations` can't get one later without losing data.

```ts
// migrations.ts
import { schemaMigrations } from 'nitromelondb/Schema/migrations'

export default schemaMigrations({ migrations: [] })
```

One model per table, in its own file. Field names are `camelCase`, column names stay `snake_case`. In TypeScript, declare fields with `!`:

```ts
// model/Post.ts
import { Model, type Query } from 'nitromelondb'
import type { Associations } from 'nitromelondb/Model'
import { field, text, date, readonly, children } from 'nitromelondb/decorators'
import type Comment from './Comment'

export default class Post extends Model {
  static table = 'posts'
  static associations: Associations = {
    comments: { type: 'has_many', foreignKey: 'post_id' },
  }

  @text('title') title!: string
  @text('body') body!: string | null
  @field('is_pinned') isPinned!: boolean
  @readonly @date('created_at') createdAt!: Date
  @readonly @date('updated_at') updatedAt!: Date

  @children('comments') comments!: Query<Comment>
}
```

```ts
// model/Comment.ts
import { Model, type Relation } from 'nitromelondb'
import type { Associations } from 'nitromelondb/Model'
import { text, relation } from 'nitromelondb/decorators'
import type Post from './Post'

export default class Comment extends Model {
  static table = 'comments'
  static associations: Associations = {
    posts: { type: 'belongs_to', key: 'post_id' },
  }

  @text('body') body!: string
  @relation('posts', 'post_id') post!: Relation<Post>
}
```

- Every field's column must exist in the schema, and optional columns must be typed `| null`.
- Associations are declared on **both** sides, keyed by the other table's name.
- Writes go in writers. If you add model methods that change data, mark them `@writer`, and see https://stasdoskalenko.github.io/NitromelonDB/docs/Writers.md before one writer calls another.

**Adding to an existing schema** (when `nitromelondb` was already installed): add a migration one version above the current `version` (`createTable` / `addColumns`), then the schema change, then bump `version`. See https://stasdoskalenko.github.io/NitromelonDB/docs/Advanced/Migrations.md. Never edit a migration that has shipped.

### 7. Create the Database

One module creates the adapter and the database, once, and exports it. Never create a second `Database` for the same file (not per screen, not on hot reload).

**React Native, Expo (including web), Windows, Node.js:** `SQLiteAdapter`. On Expo web the same import runs SQLite in the browser (wa-sqlite in a worker, stored in IndexedDB).

```ts
// db/index.ts
import { Database } from 'nitromelondb'
import SQLiteAdapter from 'nitromelondb/adapters/sqlite'

import schema from './schema'
import migrations from './migrations'
import Post from './model/Post'
import Comment from './model/Comment'

const adapter = new SQLiteAdapter({
  schema,
  migrations,
  dbName: 'app',
  // New app, no raw SQL yet: store whole numbers as INTEGER (faster comparisons and sorting)
  storeWholeNumbersAsIntegers: true,
  onSetUpError: (error) => {
    // The database couldn't open or migrate. Report it, and offer the user a way out
    // (reload, or log out and call database.unsafeResetDatabase()).
  },
})

export const database = new Database({
  adapter,
  modelClasses: [Post, Comment],
  // Throws on a writer called from another writer without callWriter(), instead of deadlocking
  experimentalDetectNestedWriters: __DEV__,
})
```

- `onSetUpError`: route it to the app's error reporting if it has one (Sentry, Crashlytics, its own logger). Don't leave it empty.
- `experimentalDetectNestedWriters`: `__DEV__` exists on React Native and Expo web. On other web bundlers and Node, use `process.env.NODE_ENV !== 'production'`.
- `dbName`: pick one for the app and never change it after release. Changing it starts an empty database.
- Don't add `jsi: true` / `jsi: false`. They're WatermelonDB options: `jsi: false` throws.
- Don't add `seed` unless the user wants demo or fixture data. On a database that already has data, every seed step still runs. See https://stasdoskalenko.github.io/NitromelonDB/docs/Advanced/Seeding.md.

**Web without Expo:** use `SQLiteAdapter` (wa-sqlite) by default, as above. Use `LokiJSAdapter` only if the user asks, or the app must support browsers without workers. Its options are in https://stasdoskalenko.github.io/NitromelonDB/docs/Setup.md (section "Web (LokiJS)"), including `onQuotaExceededError` and the multi-tab callbacks, which should be implemented, not left empty.

**Electron:** the renderer creates the `Database` with `RemoteAdapter` (step 5). The models and `modelClasses` stay on the renderer side.

### 8. Connect React

If the app uses React, wrap the root in `DatabaseProvider`:

```tsx
import { DatabaseProvider } from 'nitromelondb/react'
import { database } from './db'

export default function App() {
  return <DatabaseProvider database={database}>{/* existing tree */}</DatabaseProvider>
}
```

With Expo Router, put it in the root `app/_layout.tsx`, around the `<Stack>` / `<Slot>`.

Reads and writes made before the database is ready are queued, so the app can render right away. Gate on readiness with `useDatabaseReady(database)` (from `nitromelondb/hooks`) only if the app does work at launch that shouldn't wait silently (a splash screen it already has, auth checks that read the database, sync started on launch).

For reading data in components, point the user at `useQuery` / `useRecord` (`nitromelondb/hooks`) or `withObservables` (`nitromelondb/react`). Don't rewrite existing screens to use the database unless asked.

### 9. Check that it works

1. Run the type checker and the linter. Decorator or tsconfig mistakes show up here first.
2. Run the existing tests. Don't change unrelated failures: list them.
3. Build:
   - **Expo:** `npx expo run:ios` / `npx expo run:android`. A Metro reload isn't enough. With committed `ios/` and `android/`, autolinking is all it needs: don't run `npx expo prebuild` for NitromelonDB (it rewrites those folders), unless the user uses `excludeSimArch`.
   - **Bare React Native:** `npx react-native run-ios` (runs `pod install`) / `npx react-native run-android`.
   - **Expo web:** `npx expo export -p web`, then check that the output has a worker bundle and a `.wasm` file.
   - **Web:** the app's build command.
   - **Node.js:** run a script that imports the database module.

   Before starting a bundler, check whether one is already running on port 8081 and reuse it. Native builds take minutes: ask the user whether to run them, or hand them over.
4. **Smoke test** the first write and read, in a scratch spot you remove afterwards (a test, a dev-only button, a Node script):

   ```ts
   await database.write(async () => {
     await database.get(Post).create((post) => {
       post.title = 'Hello'
       post.isPinned = false
     })
   })
   const posts = await database.get(Post).query().fetch()
   console.log(posts.map((p) => p.title)) // ['Hello'], not [undefined]
   ```

   `undefined` here, or a dev error saying decorators aren't working, means step 4 is wrong for this compiler. See "Model fields read undefined" in https://stasdoskalenko.github.io/NitromelonDB/docs/Installation.md (Troubleshooting).

### 10. Report

Finish with a summary:

- Platform(s) detected and the package manager
- Packages added (and versions), and dev dependencies
- Config changed: Babel, `tsconfig.json`, Expo plugin, Metro, `react-native.config.js`
- Files created: schema, migrations, models, database module, where `DatabaseProvider` went
- What was run (type check, tests, builds, smoke test) and the result, and what's left for the user to run

Then tell the user, without doing it:

- **Before the first release** the schema can still change at version 1: reinstall the app (or clear its data) after each change, so the local database is created again. **After the release**, every schema change needs a migration and a version bump.
- **Expo Go** no longer runs the app. Use the development build, or EAS Build.
- **EAS Update** ships model, schema and migration changes over the air. Upgrading `nitromelondb` or `react-native-nitro-modules` needs a new build.
- **Next:** `nitromelondb-audit` once there's real data code, and `nitromelondb-indexes` once tables grow. Sync with a backend: https://stasdoskalenko.github.io/NitromelonDB/docs/Sync/Intro.md

## Checklist

- [ ] Not a WatermelonDB app (else the migration skill), not already installed
- [ ] Requirements met: RN 0.83+, New Architecture, iOS 15.1+, minSdk 24+, development build (not Expo Go)
- [ ] `nitromelondb` (and `react-native-nitro-modules` 0.35.2+ / `better-sqlite3` where needed) installed with the app's package manager
- [ ] Decorators: Expo has no decorators plugin of its own; bare React Native has the four plugins in order; web has decorators then loose class properties; `tsconfig` has `experimentalDecorators` and `useDefineForClassFields: false`
- [ ] Expo: `"nitromelondb"` in plugins. Bare React Native: no manual native linking added
- [ ] Schema with `version: 1`, an empty `schemaMigrations` passed to the adapter, one model per table in `modelClasses`
- [ ] One `Database`, with `onSetUpError` implemented, `storeWholeNumbersAsIntegers: true`, `experimentalDetectNestedWriters` in development
- [ ] `DatabaseProvider` at the root (React apps)
- [ ] Type check, tests and a build pass, and the smoke test reads back real values (or what's left is handed to the user)
