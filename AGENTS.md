# AGENTS.md

Guidance for AI coding agents (and humans) working in this repository.

## What is this project?

**NitromelonDB** (`nitromelondb` on npm) is a reactive, offline-first SQLite
database for React Native and React web — a maintained fork of
[WatermelonDB](https://github.com/Nozbe/WatermelonDB). Same lazy,
observable, SQLite-backed data model; a codebase that tracks current React
Native, iOS, Android, and Windows releases.

Key characteristics:

- **New Architecture only.** Native SQLite on iOS, Android, and Windows goes
  through [Nitro Modules](https://nitro.margelo.com). The legacy bridge
  (Paper) is not supported.
- **Single TypeScript codebase.** Implementation lives in TypeScript
  (`src/`) — there is no separate `.d.ts` layer, so types and runtime cannot
  drift.
- **Multiplatform.** iOS, Android, Windows, web (LokiJS adapter), Node.js,
  and Expo (development builds / EAS Build / EAS Update). Not usable from
  Expo Go.
- Package name is `nitromelondb`, imported as `import { Database } from
  'nitromelondb'` and `import SQLiteAdapter from
  'nitromelondb/adapters/sqlite'`.

Full docs: https://stasdoskalenko.github.io/NitromelonDB/

## Tech stack

| Area | Tech |
| --- | --- |
| Library language | TypeScript (compiled to CJS/ESM via `scripts/make.mjs`, no separate Flow/`.d.ts`) |
| Reactivity | RxJS (peer dependency), a custom `withObservables` HOC for React |
| Native bridging | [Nitro Modules](https://nitro.margelo.com) (`react-native-nitro-modules`), C++ HybridObjects, codegen via `nitrogen` (config in `nitro.json`) |
| Native SQLite engine | Vendored SQLite + simdjson in C++ (`native/shared`, `native/vendor`) |
| Web adapter | LokiJS (`@nozbe/lokijs` fork) for the web/IndexedDB adapter, `better-sqlite3` for Node.js tooling/tests |
| Mobile RN example | Expo SDK 57 (RN 0.86.2), development build (not Expo Go) |
| Windows RN example | React Native Windows 0.84 (RN 0.84.1), Fabric / WinAppSDK, C++/WinRT |
| Testing (JS) | Jest + Babel, `@testing-library/react`, `jsdom` |
| Testing (native integration) | XCTest (iOS), Android instrumented tests / Gradle (Android), Cavy + `@react-native-windows/automation`/WinAppDriver (Windows e2e) |
| Lint/format | ESLint (`@react-native/eslint-config` + TypeScript plugin), Prettier, `ktlint` for Kotlin |
| Docs site | Docusaurus (`docs-website/`) |
| Package manager | Yarn (Classic, v1) — do not introduce npm `package-lock.json` files |
| Node engine | Node.js ≥ 22 (CI uses 24.x) |

## Repository layout

- `src/` — the library implementation (TypeScript). Notable subfolders:
  `Database/`, `Model/`, `Query/`, `QueryDescription/`, `Schema/`,
  `Collection/`, `Relation/`, `adapters/` (sqlite/lokijs adapters),
  `sync/`, `react/`, `hooks/`, `decorators/`, `nitro/` (JS-side Nitro
  bindings), `__tests__/`, `__typetests__/`.
- `native/` — native bridge code:
  - `native/nitro` — Nitro HybridObject C++ glue (`HybridNitromelon*`).
  - `native/shared` — cross-platform C++ database/SQLite implementation
    shared by iOS, Android, and Windows.
  - `native/vendor` — vendored `sqlite` and `simdjson` sources.
  - `native/ios`, `native/android`, `native/windows` — per-platform native
    module projects consumed by apps via autolinking.
  - `native/iosTest`, `native/androidTest` — standalone native test harness
    projects (Xcode workspace / Android Studio project) used for
    integration tests.
- `nitrogen/` — generated Nitro codegen output (do not hand-edit; regenerate
  with `yarn specs`).
- `examples/` — **example and reference apps** (see below).
- `docs-website/` — the Docusaurus documentation site (source for the
  published docs).
- `scripts/` — build, release, and CI helper scripts (Node.js, mostly
  `.mjs`).
- `dist/` — build output of the library (generated by `yarn build`/`yarn
  dev`, not hand-edited).

## Examples

All example apps live under `examples/`. They are **not** part of the
published package and each has its own `package.json`/lockfile.

- **`examples/NotesApp`** — iOS and Android reference app. Expo SDK 57
  (RN 0.86.2) **development build** (not Expo Go). Small notes list:
  schema v2, a v1→v2 migration, create/pin/delete against a live database.
- **`examples/NotesApp_windows`** — Windows reference app. React Native
  Windows 0.84 (RN 0.84.1) New Architecture (Fabric/WinAppSDK). Kept as a
  sibling app instead of unifying with `NotesApp` because RNW and Expo
  currently track different RN minor versions.
- **`examples/benchmark`** — two Expo development-build apps
  (`nitromelondb_benchmark` and `watermelondb_benchmark`) that run an
  identical stress test (1M row writes/deletes, queries, repeated cycles)
  to compare NitromelonDB against upstream WatermelonDB on-device.
- **`examples/nitro`** — a minimal Expo app used mainly to exercise/prebuild
  the native Nitro module in isolation (generated `android/`/`ios/`
  projects).
- **`examples/typescript`** — a plain TypeScript project (no React Native)
  used to type-check the public API surface (`yarn test:typescript`).

Each example folder's `README.md` has the authoritative run instructions;
see also the platform build sections below.

## Building / compiling

Install root dependencies first (Yarn Classic):

```bash
git clone https://github.com/StasDoskalenko/NitromelonDB.git
cd NitromelonDB
yarn
```

Build the library itself (compiles TypeScript in `src/` to `dist/`):

```bash
yarn build          # production build
yarn dev            # development build, watches src/ for changes
```

To develop the library against a real app without publishing, either
symlink `dev/` into the app's `node_modules/nitromelondb` (works with
Webpack) or point the dev build directly at the app:

```bash
DEV_PATH="/path/to/your/app/node_modules/nitromelondb" yarn dev
```

(Metro does not follow symlinks, so `DEV_PATH` is required for React
Native apps.)

Regenerate Nitro codegen (`nitrogen/`, native specs) after changing Nitro
HybridObject specs:

```bash
yarn specs
```

### iOS

Requires the latest stable Xcode.

```bash
cd examples/NotesApp
yarn
npx expo prebuild
npx expo run:ios
```

For the internal native test harness (`native/iosTest`), install pods
first:

```bash
yarn cocoapods       # bundle exec pod install in native/iosTest
```

then open `native/iosTest/WatermelonTester.xcworkspace` in Xcode and build,
or run headlessly with `yarn test:ios` (see Testing below).

### Android

Requires a recent Android Studio / SDK and JDK 21 (matches CI).

```bash
cd examples/NotesApp
yarn
npx expo prebuild
npx expo run:android
```

The internal native test harness lives in `native/androidTest` (open it
directly in Android Studio, or drive it with Gradle — see Testing below).

### Windows

Windows builds are only supported via the dedicated example app —
`nitromelondb` itself has no top-level Windows build step.

Tooling (see `examples/NotesApp_windows/README.md` and
`native/windows/README.md` for full detail):

| Tool | Version |
| --- | --- |
| Windows | Windows 10 22H2+ or Windows 11 |
| Node.js | 22.11+ |
| Yarn | Classic (v1) |
| Visual Studio | 2022 (MSVC v143) or 2026 (MSVC v145), with "Desktop development with C++" and "Windows application development" workloads |
| Windows SDK | 10.0.26100 |

If Visual Studio/SDK components are missing, run (elevated PowerShell):

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\node_modules\react-native-windows\scripts\rnw-dependencies.ps1
```

Then build and run:

```sh
cd examples/NotesApp_windows
yarn install --ignore-scripts
yarn windows
```

`--ignore-scripts` is required because the library's `postinstall` belongs
to the repo root, not this example; MSBuild still generates the Nitro
header shims (`<NitroModules/…>`) before compiling. Because
`react-native-nitro-modules` has no official Windows autolink, the
NitromelonDB Windows DLL itself is the Nitro install entry point — see
`native/windows/README.md` for how that wiring works if you touch
Windows native code.

To regenerate the Windows native project after a React Native Windows
upgrade:

```sh
yarn react-native init-windows --template cpp-app --name NitromelonWindows --namespace NitromelonWindows --overwrite
```

(then re-apply the Metro / `react-native.config.js` customizations that
`init-windows` overwrites).

## Running tests

Full CI-equivalent check (Jest + ESLint + TypeScript + example
typecheck + Metro transform check + published-package self-test):

```bash
yarn ci:check
```

Individual checks:

```bash
yarn test              # Jest unit tests (src/**/__tests__)
yarn eslint            # ESLint over src
yarn typecheck         # tsc --noEmit for the library
yarn test:typescript   # typecheck the examples/typescript project
yarn test:metro-transform
```

Native integration tests (run the full library against real SQLite +
React Native):

```bash
yarn test:ios          # scripts/test-ios — needs a working iOS toolchain;
                        # open native/iosTest/WatermelonTester.xcworkspace and
                        # build in Xcode first if the terminal run fails
yarn test:android       # cd native/androidTest && ./gradlew connectedAndroidTest
                        # (or open native/androidTest in Android Studio and run
                        # com.nozbe.watermelonTest.BridgeTest)
yarn test:windows       # yarn --cwd examples/NotesApp_windows windows
yarn test:native        # iOS + Android in parallel
```

Native code linting:

```bash
yarn ktlint             # check Kotlin style
yarn ktlint:format      # auto-fix
```

Notes:

- Jest config is `jest.config.js`; tests live alongside code under
  `__tests__/` folders (pattern `**/__tests__/**/?(spec|test).js`).
- `yarn test:ios`/`yarn test:android` require a native toolchain
  (Xcode/Android Studio + emulator/simulator) and are not run in typical
  quick edit-test loops — prefer `yarn test` (Jest) for most JS/TS changes,
  and only run native integration tests when you touched `native/`,
  `src/adapters/sqlite`, or Nitro specs.
- If native tests fail from the terminal, try building/running once from
  Xcode/Android Studio first, and check Xcode CLI tools version
  (`Preferences → Locations`). Clearing caches
  (`~/Library/Developer/Xcode/DerivedData`, `.gradle`/`build` under
  `native/android*`, `node_modules`) fixes most stale-native-build issues.

## Best practices / conventions

- **Add or update tests for any behavior change.** JS/TS changes go
  through Jest (`src/**/__tests__`); native bridge or `adapters/sqlite`
  changes should also be exercised via `yarn test:ios`/`yarn test:android`.
- **Format before committing:** `yarn prettier` (writes `src` and
  `docs-website/src`). Prettier config: no semicolons, single quotes,
  100-char print width, trailing commas everywhere (see
  `prettier.config.js`).
- **Lint and typecheck must pass** — these are required CI checks
  (`yarn eslint`, `yarn typecheck`).
- **Record notable changes** in `CHANGELOG-Unreleased.md` under the
  matching section (New features / Fixes / Changes / Deprecations /
  BREAKING CHANGES / Performance / Internal). These are folded into
  `CHANGELOG.md` automatically at release time — see [Keep a
  Changelog](https://keepachangelog.com/en/1.0.0/).
- **Don't hand-edit generated output**: `dist/`, `nitrogen/` (regenerate
  with `yarn specs`), and `native/windows/**/include/NitroModules/*`
  (generated by `scripts/windows-nitro-shims.mjs`) are generated, not
  source of truth.
- **Nitro/New Architecture only** — do not add code paths for the legacy
  RN bridge (Paper). `{ jsi: false }` is intentionally rejected on all
  platforms.
- **Windows and Expo/iOS/Android examples are intentionally split**
  (`NotesApp` vs `NotesApp_windows`) because they track different React
  Native minor versions; don't try to unify their `package.json`s.
  Windows examples use `yarn.lock` (Yarn Classic) — never introduce npm's
  `package-lock.json` there.
- **Keep JS runtime and types in sync** — this is a single TypeScript
  implementation with no separate `.d.ts` authoring; avoid reintroducing a
  parallel type-only layer.
- Recommended editor setup: VS Code with ESLint, TypeScript, and Prettier
  extensions for inline lint/type feedback and format-on-save.
- See `CONTRIBUTING.md` for the full pre-PR checklist and native code
  troubleshooting tips, and the [docs site](https://stasdoskalenko.github.io/NitromelonDB/)
  for architecture/usage documentation (source in `docs-website/docs`).
